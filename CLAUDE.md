## Статус проекта

Stage 1 (foundation / shell) и Stage 2 (hero scene) готовы, стиль города утверждён пользователем. В hero — живой район (граф `src/simulation/graphs/city.ts`): процедурные здания по типам узлов, фоновая застройка, трафик, потоки данных, статус-карточки и хореография запроса client → gateway → API → DB → обратно с карточкой результата.

Stage 3 готов. 3a — симуляция и playground на `/architecture`: 8 сценариев (sync, cache, 422, 401, 429, async job, retry, DLQ), composer с JSON и проверкой как в FastAPI, трасса, логи, ответ, пауза / шаг / скорость / пошаговый режим, пакеты и карточки на сцене, работа без WebGL. 3b — взаимодействие со сценой: hover по зданию (focus mode + подсказка), клик → DOM-инспектор узла (контент в `content/nodes.ts`), список «Компоненты системы» для клавиатуры, подсветка узла по hover на спане, «Отправить запрос» в hero.

Stage 4a готов: районы стека в том же мире (Frontend — внизу слева вокруг клиентов, Automation & AI — внизу справа вокруг планировщика и мониторинга; Scheduler переехал туда), ракурсы камеры с перелётами, страницы `/stack/[area]` со сценой района и связью «технология ↔ здание» в обе стороны. Stage 4b готов: на каждой странице района — сценарии на его сцене с пояснениями к шагам (backend: запросы playground + вебхук с идемпотентностью и «когда что выбираю»; frontend: SSR-стриминг, валидация на клиенте и сервере, optimistic UI; automation: бот запускает синхронизацию, сбой внешнего API, Docker-образ) и код-сниппет. Stage 4c готов: в playground 12 сценариев — добавлены circuit breaker, идемпотентный вебхук, fan-out и chaos (упавший воркер и автоскейл). Stage 4 закрыт.

Плюс перекрёстные ссылки (кейс ↔ стек и сценарии, «Кейсы с этим компонентом» в инспекторе) и форма контакта → Server Action → Telegram с антиспамом.

Stage 6 готов: один английский сайт в корне (без `[lang]`, переключателя, hreflang и proxy), две аудитории — `/for-employers` (инженерный профиль) и `/hire` (шесть услуг) с посадочными `/services/[slug]` (python-backend, ai-rag, full-stack, automation), `/privacy`, `/stack` → `/expertise`. Technical SEO: canonical, OG/X с картинкой на каждой странице (у кейсов — своя), sitemap из реальных маршрутов, robots закрывает всё, кроме production, JSON-LD (WebSite, Person при заданном имени, BreadcrumbList, Service). Дальше — запуск по чек-листу (`docs/stage-6/11-launch-checklist.md`) и Stage 7.

Stage 7, этап 1 готов: живой бэкенд в `backend/` (uv workspace) — Orders API на FastAPI с PostgreSQL и Redis в Docker Compose. В playground режим «Live API» (`NEXT_PUBLIC_LIVE_API_URL`) для пяти сценариев (sync-read, cache, validation, auth, rate-limit): запрос уходит в настоящий сервис, сцена воспроизводит его настоящую трассу. Без аккаунтов и персональных данных: анонимная песочница на 30 минут.

Stage 7, этап 2 готов: RabbitMQ (quorum-очереди, отложенные повторы через TTL-очереди, DLQ, обратное давление), `order-worker` в двух репликах и заглушка платёжного провайдера (`provider-stub`: `Idempotency-Key`, внедрение сбоев `X-Fault-Fail-Attempts`). Live API покрывает ещё три сценария — `async-job`, `retry`, `dead-letter`: ответ 202 играет сразу, спаны воркера сайт забирает опросом трассы и доигрывает как продолжение того же прогона. Вебхук и circuit breaker переехали в этап 3: в городе они идут через «Payments API · Django».

Stage 7, этап 3a готов: Payments API на Django (`backend/services/backoffice`) — checkout с circuit breaker вокруг провайдера (состояние в Redis, Lua, общий для реплик, отдельный на песочницу), подписанный HMAC идемпотентный вебхук провайдера с конечным автоматом статусов платежа, админка владельца только на 127.0.0.1:8001; единая точка входа `edge` (Caddy): `/webhooks/*` → Django, остальное → FastAPI. Live API покрывает ещё `circuit-breaker` и `webhook` (вебхук подписывает страница WebCrypto-ключом песочницы).

Stage 7, этап 3b готов: события заказов через Kafka. `POST /api/orders` пишет заказ и событие `order.created` в `orders.outbox` одним SQL; `outbox-relay` (`orders-api-relay`, образ Orders API) публикует их в топик `orders.events` (3 партиции, ключ — id заказа, `acks=all`, идемпотентный продюсер); три consumer group в `order-worker` (inventory → `orders.reservations`, analytics → `orders.daily_sales`, notifications → Redis) идемпотентны и коммитят offset после работы. В городе — здание Kafka рядом с RabbitMQ; fan-out переехал на Kafka (RabbitMQ — задачи и команды) и стал live.

Stage 7, этап 3c готов: push по WebSocket — только события своей песочницы (решение пользователя). Сервис `realtime-hub` (`backend/services/realtime-hub`, FastAPI, две реплики, edge `/ws`) — здание Notifications: держит сокет страницы, пушит уведомления (`report.ready`, `payment.succeeded`/`failed`, `order.created`) и сигнал `trace.done`. Страница забирает трассу по сигналу хаба, опрос — запасной путь; в городе live-push рисуется, только если хаб записал спан `push`.

Stage 7, этап 4 готов: Flask-бот владельца (`backend/services/ops-bot`, решения пользователя: webhook во Flask через edge `/telegram/*` на сервере, long polling локально; оповещения только о настоящих проблемах). Команды `/status`, `/dlq` (с кнопкой повтора DLQ), `/alerts`; `ops-bot run` раз в 30 с проверяет систему и пишет владельцу о новых и снятых проблемах. Токен и id владельца не заданы — пользователь добавит их в `backend/.env`.

Stage 7, этап 5 готов: нагрузка (Locust), chaos-эксперименты и страница `/architecture/report` с настоящими замерами (решения пользователя: отдельная страница, локальные замеры с подписью среды, выкладка на VPS подготовлена, но не выполнена). Эксперименты нашли и исправили две проблемы (500 без Redis → быстрый 503; потеря первой команды на старом соединении Redis → повтор у всех клиентов). Для VPS — `backend/compose.prod.yaml`, `infra/edge/Caddyfile.prod` и runbook `docs/stage-7/vps-deploy.md`; выкладывать только на сервере пользователя и с его согласия. Stage 7 закрыт.

Правила сцены, которые легко сломать:

- Глубина: здания, деревья и машины в одном слое `entities`, `zIndex = depthKey(центр)`. Это корректно, только пока `|width − depth| ≤ 0.8` и здания отстоят от дорог на ≥ 0.3 тайла — схема графа это проверяет, не ослабляй её.
- Подписи на сцене — технические идентификаторы (`Orders API`, `200 OK`); смысловой текст — только в DOM.
- Фоновые здания (`planDecor`) рисуются приглушённой палитрой `backgroundPalette`: насыщенный цвет остаётся за узлами системы. Они не заходят в `views.system.area` (ядро, скомпонованное для hero и playground) и держатся в стороне от узлов и наземных связей.
- Ракурсы камеры — `views` графа (`hero`, `system`, `backend`, `frontend`, `automation`): область кадра и, для района, его узлы (остальной город приглушается). Каждый `SceneViewport` объявляет свой `view`; смена ракурса — команда `setView`, камера летит 900 мс (`camera/flight.ts`: прямая по мировой точке под центром кадра, зум геометрический). Не кадрируй сцену вычислением границ узлов на месте — заведи или поправь ракурс в графе.
- Перед перелётом с приближением арт перепекается под конечный зум заранее — запечённую текстуру нельзя растягивать даже на время полёта.
- Карточки живут в экранных координатах (`overlay`), чтобы текст был чётким; видимость — по безопасной зоне кадра.
- Отступы кадра (`FOCUS_INSET_ATTRIBUTES` в `engine/types.ts`, проп `focusInsetsLarge` у `SceneViewport`) — со всех четырёх сторон, только на `lg`: доля оси или пиксели; противоположные стороны вместе оставляют сцене не меньше 35% оси (`camera/focus-inset.ts`). Камера кадрирует город в свободной части, карточки не заходят в отступы; изменённый атрибут движок ловит `MutationObserver` и перелетает на новое место (так сворачиваются панели). Отступ — из состояния страницы и измеренных стабильных размеров, а не из анимируемых коробок: иначе перекадрирование и перепекание на каждом кадре.
- Страница может прикрепить DOM к зданию: `useStage().trackNode(nodeId, listener)` отдаёт экранную точку над крышей (где подпись) при каждом движении камеры — позиционируй через `transform` по ref, без React state. `markNode(nodeId)` рисует пульсирующее кольцо вокруг здания (`views/node-beacon.ts`, своя render group, кадр меняет только transform и alpha); пока кольцо стоит, фоновые карточки мира скрыты — на сцене один призыв к действию.
- Производительность: статичная векторная графика (здания, деревья, машины, импульсы) не живёт как `Graphics` в динамических слоях — она запекается через `TextureBaker` в масштабе отображения и рисуется спрайтами. Иначе PixiJS каждый кадр перепаковывает тысячи вершин (`packAttributes` был главным горячим местом). Неподвижные слои — в отдельной render group. Любую заметную правку сцены проверяй `npm run perf:scene` (бюджет: ≤ 30 draw calls, без кадров > 50 мс).
- `TextureBaker` ставит запекаемому `Graphics` `batchMode = "batch"`: такой арт рисуется только при запекании, а «большой» контекст в режиме `auto` PixiJS рисует отдельно и держит его bind group в глобальном кэше — уничтожение градиентов вместе с миром кейса тогда сыпало в консоль `[BindGroup] … destroyed while still bound`. Не убирай это. Консоль сцены проверяется прогоном по страницам в настоящем Chrome с GPU (клиентские переходы между кейсами — обязательно).
- Ввод сцены — только через `engine/input/PointerInput` (тап отличается от скролла и pinch через `TapTracker`). Встроенный EventSystem PixiJS отключён (`setTargetElement(null)` в `create-stage.ts`) — не включай его: он ставит canvas `touch-action: none` (на телефоне страница перестаёт листаться пальцем по сцене) и каждый кадр делает hit-test всей сцены. Попадание в здание — геометрия силуэта (`world/node-picking.ts`), а не границы спрайта.
- Focus mode (`views/node-focus.ts`): подсветка связей и кольца — `Graphics` в собственных render group, перерисовываются только при смене фокуса, не каждый кадр.
- Запечённую текстуру нельзя растягивать: спрайт со scale > 1 размывается. Арт, которому нужно расти (кольца-импульсы, пакеты playground на узком кадре), рисуется в максимальном размере и только уменьшается — см. `PACKET_ART_SCALE` в `engine/views/packet-art.ts`.

Симуляция и playground — как устроено и что не ломать:

- Сценарий — данные (`simulation/scenarios/catalog.ts`). `SimulationSession` компилирует его в детерминированный `ScenarioRun` — таймлайн `SimEvent` (`simulation/model/events.ts`); состояние между запросами (кэш с TTL, token bucket) живёт в сессии. Время анимации замедлено (~9×), а в спанах и ответе — реалистичные `reportedMs`.
- `TracePlayer` — единственные часы прогона (пауза, шаг, скорость). Движок получает его как `PlayerHandle { time, subscribe }` через `useStage().connectPlayer(player, mode)` и позиционирует пакеты только от `player.time`. Режим `"playground"` кадрирует всю систему и глушит фоновую историю, `"visitor"` (кнопка в hero) оставляет hero как есть и только ставит на паузу скриптовый запрос. Будущий live-источник (FastAPI по WebSocket) обязан реализовать тот же интерфейс — не протаскивай в движок знания о симуляции.
- `PlaygroundController` (`features/playground`) держит свой rAF-цикл и vanilla zustand store; события сводятся в store один раз за кадр, плейхед трассы двигается через `onFrame` по ref, без ререндера React. DOM-панели работают и без canvas — это проверяет e2e.
- Состояние сессии между запросами: кэш с TTL, token bucket, предохранители по связям (`runtime/circuit-breaker.ts`: closed → open → half-open, время — wall time) и обработанные id событий для идемпотентности. «Сбросить кэш и лимиты» очищает всё это. Фоновая работа (задачи с ретраями, fan-out, пачки задач с автоскейлом) — в `runtime/background-work.ts`; `session.ts` отвечает за путь запроса.
- Сценарии с историей между отправками (circuit breaker) идут по одному запросу на отправку: пояснения показываются только для активного прогона, а у пачки прогоны идут внахлёст.
- Карточки прогонов не прячутся у края кадра, пока их здание видно, — они сдвигаются внутрь; фоновые карточки у края по-прежнему скрываются.
- Истории районов (`simulation/stories/catalog.ts`) — сценарии без ввода и состояния: шаги `hop` / `work` / `status` / `note` / `log` / `pause` / `together`. `runtime/story-compiler.ts` компилирует их тем же `RunBuilder` в обычный `ScenarioRun`, так что плеер, сцена и пояснения общие с playground; пояснение держится на экране не меньше `NOTE_MIN_MS`. Что предлагает страница района, задаёт `districtEntries` (истории и запросы playground). Узлы и пакеты истории должны оставаться в кадре своего района — иначе карточки и пакеты улетают за экран.
- Связи с `quiet: true` не рисуются в покое (ни в городе, ни в подсветке района): их показывают только пакеты прогона и наведение на узел. Так добавляются пути для историй (вебхук, выкладка, алерт), не засоряя hero.
- Пока над узлом висит карточка прогона, фоновая карточка этого узла скрыта.
- Страница района и кнопка в hero берут сцену через `useScenePlayer` (режим `"visitor"`): плеер подключается на время прогонов и отпускается после них.
- Порядок блоков playground в DOM — мобильный (сцена → плеер → composer → сценарии → результаты); две колонки на desktop задаются grid-размещением, а не CSS `order`.

Выбор узлов и инспектор:

- Источник правды — vanilla zustand-store в `StageProvider` (`features/stage/stage-store.ts`): `selectedNodeId` и `previewNodeIds`. Тап по сцене приходит событием `StageEvent`, любое изменение store уходит в движок командой `StageCommand` (`selectNode`, `previewNodes`). Компоненты пользуются `useStageSelection` / `useNodeActions`, напрямую в движок не ходят.
- Выбор принадлежит странице: инспектор очищает его при размонтировании. При открытии фокус переходит на заголовок инспектора, Escape и крестик возвращают его туда, откуда пришёл посетитель.
- Контент инспектора — `content/nodes.ts` (профиль на узел, воркеры делят один; тест проверяет, что у каждого узла графа ровно один профиль). У узла графа есть `tech` — технический ярлык для сцены. «Сценарии через узел» не пишутся руками: их выводит `simulation/scenarios/footprint.ts`, прогоняя каждый сценарий.
- `?scenario=<id>` на `/architecture` запускает сценарий при заходе (ссылки из инспектора и hero); параметр проверяется Zod в `features/playground/scenario-param.ts`.

DRF и WebSocket — только там, где пользователь подтвердит реализацию. Celery/RQ, CI/CD, blue-green, cron, Nginx, Prometheus, JWT как навыки на сайте не заявляются: это было в первом брифе, но не вошло в профиль.
- Город — демонстрация паттернов (ретраи, DLQ, circuit breaker в playground), а не перечень инструментов. Подписи зданий нейтральные (`Worker · Python`, `Docker Build`, `Sync Job`).
- У каждой технологии стека есть здание района, опубликованный кейс или `shownAt` — раздел сайта, где она показана (AI-assisted → `/projects#ai-workflow`); тест это проверяет. Технологии без здания (AI/Data, сети, облако) ведут на кейсы, а список технологий района показывает ссылки «В кейсах».

Кейсы и мини-города:

- Факты кейсов — только подтверждённые пользователем (стек кейса он подтвердил явно). В тексте кейсов нет выдуманных чисел, клиентов и результатов; цифры в демо считает модель, и демо подписано как симуляция на синтетических данных. Кейс 05 — обобщение опыта (`note`), RabbitMQ и Kafka в демо не смешиваются.
- Кейс — это:
  - `content/cases/<slug>.ts` — запись реестра (`CaseRecordInput`), включая `basis` (`project` — одна система, `practice` — обобщение опыта), тексты демо (`{ru, en}`; отдаётся только `en`) и `<slug>Glance` — блок «At a glance» (только английский; в `projects.ts` он садится в поле `glance`);
  - `content/cases/<slug>.en.mdx` — история: Problem, Solution, My role, Technical architecture, Implementation, Functional outcome (без frontmatter). `.ru.mdx` — архив, на сайт не попадает;
  - `simulation/cases/<slug>/` — `graph.ts` (мир), `model.ts` (чистая логика), `compile.ts` (модель → прогон), `impact.ts` (сравнения для графиков glance), тест;
  - `features/cases/<slug>-demo.tsx` — клиентское демо.

  Новый кейс регистрируется в трёх местах: `simulation/graphs/worlds.ts`, `content/projects.ts`, `features/cases/case-demo.tsx`.

- «At a glance» (`features/cases/case-glance.tsx`) — то, что прочтут HR и заказчик: 2–3 пункта «до» и «после» и «What I did» — пересказ подтверждённой истории кейса, без новых утверждений; 1–2 графика. `CaseGlanceStrip` — карточки Before / After / графики (на десктопе полоса поверх низа города), `GlanceSteps` — «What I did» в блоке под городом. Цифры графиков не пишутся руками: их считает модель кейса (`simulation/cases/<slug>/impact.ts`) — та же работа без приёма и с ним (без кэша / с кэшем, 1 воркер / 3, сырые данные / очищенные), на синтетических данных, и страница это подписывает. Реальных замеров у кейсов нет; если пользователь даст настоящие цифры, для них есть поле `metrics` («Results in numbers»). Схема (`caseGlanceSchema`) проверяет, что у каждого столбика есть подпись, что последний столбик — улучшение относительно первого и что выбранная большая цифра (`ratio` / `reduction` / `after`) определена.
- Анимация glance — прогрессивная: сервер рисует финальное состояние; то, что видно при загрузке, проигрывается CSS-анимацией с первой отрисовки (`animate-rise-in`, `animate-bar-grow`, `backwards`), то, что ниже экрана, `Reveal` прячет и проигрывает при прокрутке (`data-reveal`), большая цифра считает вверх (`CountUp`, прямо в DOM на rAF, без state). С reduced motion и без JS всё сразу на месте. Полная история — в `<details class="disclosure">` «Engineering details»: в DOM и в поиске, но свёрнута; высота анимируется через `::details-content` + `interpolate-size` (где нет поддержки — открывается сразу), содержимое всплывает везде.

- Миры: `worldGraphs` — город и миры кейсов (`worldGraphSchema`: ракурс `system` обязателен, можно добавить районы, как `rabbitmq` / `kafka`). Слот сцены объявляет `SceneRef` (`{ world, view }`), команда — `setScene`: внутри мира камера летит, другой мир заменяет сцену сразу. Город кэшируется, мир кейса строится заново и уничтожается при уходе. Канвас по-прежнему один.
- Миры кейсов собираются помощниками `simulation/cases/layout.ts` (здание, маршрут по полосе, полосы машин): перекрёсток из двух дорог, связи по осям сетки. Диагональная связь на экране ложится поверх соседнего здания. Повторяющиеся связи (партиция → consumer) — `quiet`.
- `nameTags: true` в графе мира — постоянные подписи над зданиями (`engine/views/name-tag.ts`, экранные координаты). Под карточкой прогона подпись прячется. У города подписей нет.
- Прогон кейса пишется через `CaseScript` (`simulation/cases/case-script.ts`) поверх `RunBuilder`: те же события, что у playground. Подписи к шагам — ключи с параметрами (`{count}`), текст живёт в контенте кейса и показывается в DOM (`CaseStage`). Общий `NoteKey` playground не расширяется.
- `CaseController` и `PlaygroundController` делят `PlaybackClock`; `useScenePlayer` принимает любой `ScenePlayback`. Демо кейса занимает сцену в режиме `"playground"`: фоновые карточки мира уступают карточкам прогона.
- Карточка кейса в списке показывает кадр настоящей сцены — `public/cases/<slug>.jpg` (`casePosterPath`). Кадры снимает `npm run posters:cases` с запущенной production-сборки (страница кейса с reduced motion, ширина ниже `lg`, слот 4:3); после правки мира кейса или вида сцены их переснимают, тест проверяет, что кадр есть у каждого кейса. Постер до загрузки движка и без WebGL в слотах сцены — по-прежнему `ScenePoster` того же графа.
- Раскладка страницы кейса — `CaseStage` (демо передаёт панели детьми, страница через `CaseDemo` — блоки `title`, `intro`, `glance`). Один DOM-порядок для обоих размеров: title → intro → glance → «How it works» → сцена → панель. На телефоне это колонка. На десктопе первая строка grid — город на первый экран, и title / glance / панель лежат в той же ячейке (grid-размещение, не CSS `order`): title по центру сверху, glance-полоса снизу, панель слева (`lg:w-[27rem]`, своя прокрутка); intro — во второй строке под городом. Панель сворачивается влево (ручка `Hide the panel`), полоса — вниз (кнопка `At a glance`); где места мало (уже `xl` или ниже 900 px), полоса стартует свёрнутой — CSS-вариант `glance-folded` (globals.css) до гидратации и `ROOMY_QUERY` в JS для отступа камеры, держи их одинаковыми. Отступы камеры: слева `PANEL_INSET` (480) / `COLLAPSED_INSET` (76), сверху и снизу — по измеренной высоте карточки названия и полосы. Меняешь размеры оверлеев — меняй константы в `case-stage.tsx`.
- Точка отправки — проп `entry` у `CaseStage` (`SceneEntry`: `text` с мини-вводом или `action` с кнопкой; то же действие, что главная кнопка панели): кольцо вокруг здания и пузырь «Try it here» над его подписью (`scene-entry.tsx`), прижатый к свободной части сцены; во время прогона пузырь прячется — его место занимают карточки прогона. Только на `lg`: на телефоне панель и так под маленькой сценой. Узлы: KB — `kb.client`, наука — `sd.data`, автоматизация — `pa.api`, мессенджер — стол-отправитель, event-driven — `ed.api` / `ed.producer` по району, веб — `wa.browser`, данные — `di.client`, боты — `bi.user`.
- `published: false` — черновик: виден в dev, в production его нет в списке, sitemap и инспекторе, страница — 404 (e2e это проверяет). Пока опубликованных кейсов нет, `generateStaticParams` отдаёт заглушку `_none`: с Cache Components пустой список роняет build. Не удаляй её.

Живой бэкенд (`backend/`) и режим Live API — как устроено и что не ломать:

- `backend/` — uv workspace. Библиотеки: `libs/contracts` (форматы: `Trace` с фоновой частью, сообщения задач `ReportJob`/`ChargeJob`, ключи трасс в Redis), `libs/telemetry` (`span`, рекордеры, JSON-логи — общие для всех сервисов), `libs/messaging` (топология RabbitMQ как код и публикация с подтверждением). Сервисы: `orders-api` (FastAPI; в том же образе — `orders-api-relay`), `order-worker`, `realtime-hub` (FastAPI WebSocket), `provider-stub`, `backoffice` (Django: Payments API и админка), `ops-bot` (Flask, Telegram-бот владельца). Публичный вход — `edge` (Caddy, `backend/infra/edge/Caddyfile`). Один `.venv` и `uv.lock`; у каждого сервиса свои зависимости и свой образ из общего `backend/Dockerfile` (`--build-arg SERVICE=<name>`). Новый член workspace — добавить его `pyproject.toml` в `Dockerfile` и пути в `pyproject.toml` (ruff, mypy, pytest). Подробности — `backend/README.md`.
- Трасса: сервис оборачивает каждый шаг в `span(kind, name)` (`rate_limit`, `auth`, `validate`, `handle`, `cache_get`, `cache_set`, `db`); имя — реальная операция (SQL, команда Redis) без значений. Трасса хранится в Redis 5 минут (`GET /api/traces/{id}`), в ответе — `X-Trace-Id` и `Server-Timing`. Порядок проверок на входе тот же, что в городе: rate limit → auth.
- Воспроизведение: `SimulationSession.replay(input, clock, exchanges)` компилирует трассу тем же компилятором, что и симуляцию: шаги сценария задают путь по городу, трасса — решения (кэш, лимит, токен, валидация), миллисекунды и ответ. `LiveTraceCursor` выдаёт спаны по виду в порядке записи; шаг без своего спана пропускается. Состояние симуляции (кэш, token bucket) live-прогоны не трогают. Движок о live-режиме не знает.
- Контракт: `contracts.Trace` (Pydantic) ↔ `liveTraceSchema` (Zod, `simulation/live/live-exchange.ts`). Фикстуры `backend/libs/contracts/fixtures/*.json` записаны с настоящего сервиса (`backend/scripts/record_fixtures.py`); их проверяют pytest (сервис ведёт себя как записано), Vitest (фикстура воспроизводится) и e2e (моки `page.route`). Изменил поведение сервиса — перезапиши фикстуры.
- Новый live-сценарий: маршрут в `orders-api` со спанами → id в `liveScenarioIds` → фикстура → тесты. Сценарии без live-реализации в режиме Live API честно остаются симуляцией.
- Очереди: топология объявляется одинаково в API и воркере (`messaging.Topology`); аргументы очередей менять только там — брокер отклонит повторное объявление с другими аргументами. Обратное давление: у quorum-очереди лимит мягкий (отказ, когда длина _превысила_ `max_queued`), API отвечает 503 с `Retry-After` и помечает задачу `rejected`. Задача пишется в `orders.tasks` до публикации; сообщение подтверждается (ack) только после того, как следующий шаг сохранён (итог задачи, копия в retry-очереди или в DLQ) — доставка at-least-once, поэтому обработчики идемпотентны (ключ идемпотентности у провайдера = id задачи, завершение задачи только из `queued`).
- `Broker.connect` создаёт `RobustConnection` сам и закрывает его при неудаче или отмене: у `connect_robust` цикл переподключения переживает отмену первой попытки и вешает остановку event loop (так зависали тесты). Не возвращай `connect_robust`.
- Фоновая трасса: воркер дописывает спаны (`consume`, `external`, `retry`, `dead_letter`, `db`, `notify`; хаб — `push`) в `trace:{id}:background` на часах запроса и ставит `…:done` (у события заказа участников четыре — relay и три группы, `finish_part` считает их в `…:background:finished`; спаны групп помечены атрибутом `group`, `load` сортирует фон по началу); `GET /api/traces/{id}` склеивает. На сайте `SimulationSession.replay()` возвращает прогоны и `pending`; `PlaygroundController` ждёт трассу (`LiveApi.awaitBackground`: с открытым сокетом — по сигналу хаба `trace.done` или раз в 3 с, без сокета — опрос 2 раза в секунду, до 30 с) и планирует `pending.resume()` — продолжение с тем же `runId` (`RunBuilder.build()` отдаёт события с прошлого вызова). `runtime/live-background.ts` рисует только то, что было в трассе: push — только при спане `push` от хаба, алерта мониторинга в live нет.
- Внедрение сбоев: контрол «Provider failures» в live шлёт `X-Fault-Fail-Attempts`, «Provider not responding» — `X-Fault-Provider-Down` (Orders API → Django → заглушка, которая молчит дольше таймаута); провайдер — заглушка, в UI это сказано.
- Payments API (Django): своя схема `backoffice` (миграции Django; таблицы `orders.*` только читает — модель `Task` с `managed = False`). Спаны: каждый SQL ORM — через `connection.execute_wrapper`; вызванный Orders API (заголовки `traceparent` и `X-Trace-Started-At`) дописывает спаны в `trace:{id}:remote`, `TraceStore.load` склеивает по времени; как точка входа (вебхук) хранит трассу сам. `/internal/` — только с `X-Internal-Token`, edge его не маршрутизирует.
- Realtime hub: протокол — `contracts.realtime` (Pydantic) ↔ Zod в `features/playground/live-events.ts`. Токен песочницы — только первым сообщением `auth` (не в URL); проверка `Origin` до accept; закрытие кодами 4401/4408/4410/4429/1008/1013 (страница по ним решает, переподключаться ли). Производители уведомлений — `messaging.notifications.Notifier` (один Lua: маркер `SET NX`, входящие `notifications:<client>`, `PUBLISH events:<client>`); уведомления только для владельцев-песочниц (`t:…`). Порядок — контракт: уведомление публикуется до `BackgroundTraces.finish` (тот публикует `traces:done`), хаб обрабатывает сообщения Redis строго по одному, поэтому спан `push` уже в трассе, когда страница получает `trace.done`. Pub/sub ничего не хранит: первый запрос новой песочницы ждёт открытия сокета (`LiveEvents.whenOpen`, ≤ 1 с), после переподключения страница заново шлёт `watch`. Сокет закрывается вместе с playground (`pauseEvents` в `stop()`). Тесты хаба — настоящий uvicorn в процессе теста (`testing/hub_harness.py`), стенд `full_stack` включает хаб; фикстуры пишутся с открытым сокетом через edge. После правки Caddyfile перезапускай `edge`: `up -d` его не пересоздаёт.
- Ops-бот: два процесса одного образа — `ops-bot serve` (Flask под gunicorn: `POST /telegram/webhook` с проверкой `X-Telegram-Bot-Api-Secret-Token` через `hmac.compare_digest`, `/healthz`) и `ops-bot run` (проверки, оповещения, при `transport=polling` — команды через `getUpdates`). Отвечает только `owner_ids` в личном чате, чужим — ничего. Все операции async (`ops_bot/ops.py`), каждое чтение ограничено по времени, недоступная часть попадает в `unreadable`, а не роняет отчёт; БД — SQLAlchemy + asyncpg (psycopg async не работает на Windows-цикле `Proactor`). Повтор DLQ: сброс задачи `failed → queued` в транзакции, открытой до подтверждения публикации (воркер ждёт блокировку строки), ack письма — после коммита, задача песочницы, которой нет, — письмо удаляется. Кнопка повтора — одноразовый nonce в Redis на 5 минут. Оповещения (`alerts.py`): чистая `find_problems` + `AlertBook` в Redis (`diff` → отправка → `record`, так неотправленное повторится); демо-сбои (`fail_attempts > 0`) и breaker песочницы не оповещают. Токен Telegram — в пути Bot API, поэтому telemetry глушит INFO-лог httpx для всех сервисов. Пустые env-переменные бота считаются незаданными (`env_ignore_empty`). Тесты: `testing/telegram_double.py` (Telegram без сети), `testing/ops_fixtures.py`, повтор DLQ — на стенде `stack`.
- Замеры и отчёт: `backend/scripts/locustfile.py` (профиль посетителя), `run_load.py` и `run_chaos.py` пишут `src/content/reports/load.json` и `chaos.json`; их читает `content/reports.ts` (Zod при загрузке модуля) и показывает `/architecture/report`. Цифры не правятся руками — только перезапуском скриптов. На время прогонов `compose.load.yaml` снимает лимиты «на посетителя» (одна машина и один IP играют всех) и после прогона стек возвращается к обычным лимитам; в production этот файл не используется. Рассказ о находках chaos (`report.chaos.findings` в словаре) — по id эксперимента, тест проверяет, что такой эксперимент есть. Клиенты Redis во всех сервисах создаёт `telemetry.redis_client` (повтор при обрыве соединения: после перезапуска Redis первая команда на старом соединении иначе терялась); у Orders API таймаут Redis 0,5 с и обработчик `RedisError` → 503 с `Retry-After`, трасса в упавший Redis не пишется. Production: `docker compose -f compose.yaml -f compose.prod.yaml up -d --build`, секреты без значений по умолчанию (`${VAR:?…}`), наружу только edge 80/443.
- Сайт в production — сервис `site` в `compose.prod.yaml` (контекст сборки — корень репозитория, `Dockerfile` и `.dockerignore` там же). `NEXT_PUBLIC_*` приходят build args из `backend/.env` (адреса сайта и API и индексацию compose выводит из `SITE_DOMAIN` / `API_DOMAIN`), токен бота формы — build secret `contact_telegram_bot_token` (страница контактов статическая, а в слои образа токен попасть не должен), в рантайме — env. Standalone-вывод включает только `NEXT_BUILD_OUTPUT=standalone` (Dockerfile): локальная сборка и e2e остаются на `next start`. Контейнер read-only, писать можно только в том `site-cache` (`.next/cache`). CORS API и Origin сокета собираются из `SITE_DOMAIN` — отдельного `SITE_ORIGIN` нет.
- События (Kafka): брокер — `apache/kafka:4.1.0` в KRaft, один узел, автосоздание топиков выключено (`messaging.kafka.ensure_topic` создаёт топик с партициями; его зовут и relay, и воркер). aiokafka без типов — трогает его только `messaging/kafka.py`. Outbox: заказ и событие — один SQL (CTE), заказ не ждёт Kafka и отвечает 201 и без неё. Relay забирает строки `FOR UPDATE SKIP LOCKED`, публикует и помечает в одной транзакции; отказ посреди пачки откатывает её целиком, спаны relay пишутся только после коммита (повтор не задваивает трассу). Группы: отметка «обработано» и работа — один SQL (`orders.processed_events`) или один Lua (`SET NX` для notifications); offset коммитится после работы; сбой БД — повтор того же события (партиция ждёт, порядок сохраняется). Каждая реплика воркера — участник всех трёх групп. Тесты событий — фикстура `event_stack` (relay в процессе, Kafka из compose на 127.0.0.1:9094, топик и группы с префиксом `test.`).
- Вебхук: песочница при создании отдаёт `webhook_secret` (в Redis вместе с записью песочницы, формат — `contracts.SandboxRecord`); подпись `Webhook-Signature: t=…,v1=HMAC-SHA256("t.body")` по точным байтам (`contracts.webhooks`), допуск 5 минут; событие пишется под уникальным `(owner_key, event_id)`, переход платежа — одним SQL по `TRANSITIONS`, недопустимый переход → 409 и откат.
- Компилятор: шаги `publish`, `guardedCall`, `dedupe`, `fanout` живут в своих модулях (`runtime/publish-step.ts`, `guarded-call.ts`, `dedupe-step.ts`, `fanout-step.ts`) и получают `StepContext` (`runtime/step-context.ts`); `session.ts` — оркестратор пути запроса. Новый шаг со сложной логикой — в свой модуль, не в `session.ts`.
- Приватность — часть архитектуры: в live API нет полей с персональными данными (тело заказа — product, quantity, delivery; так же в симуляции). Токен песочницы — только в памяти страницы, сервер хранит его SHA-256; IP — только HMAC с ключом, который меняется каждые сутки; access log выключен; Redis без persistence; заказы песочницы удаляются по истечении. Раздел Live API в `/privacy` появляется, только если задан `NEXT_PUBLIC_LIVE_API_URL`.
- Браузерный клиент (`features/playground/live-api.ts`) не задаёт `fetch` режим кэша: `cache: "no-store"` заставляет браузер слать `Cache-Control: no-cache`, и сервис честно обходит кэш. Ответы API сами помечены `Cache-Control: no-store`.
- Локально живой режим включает `.env.development.local` (`NEXT_PUBLIC_LIVE_API_URL=http://localhost:8000`, только `next dev`); production-сборка без переменной — чистая симуляция.
- Python: ruff (format + lint), mypy strict, pytest (`asyncio_mode = auto`). Интеграционные тесты — против Compose (PostgreSQL на 127.0.0.1:5433, Redis на 6380, RabbitMQ на 5673), отдельная БД `runtime_city_test`, Redis DB 15 и очереди с префиксом `test.`; без хранилищ они пропускаются, с `REQUIRE_INTEGRATION=1` падают. Общие фикстуры всех сервисов — один `backend/conftest.py` (он же настраивает Django на тестовые хранилища; несколько conftest mypy считает одним модулем). Стенд — `backend/testing/stack_harness.py` (на `pythonpath` pytest: под `--import-mode=importlib` тесты не могут импортировать conftest): API, Django через ASGI, воркер и заглушка в одном процессе; провайдер для Django — `httpx.MockTransport` с поведением заглушки. Сквозные тесты задач — `-m broker`.
- Фикстуры пишутся по HTTP с работающего compose-стека через edge (`docker compose up -d --build`, затем `scripts/record_fixtures.py`), одна песочница со сбросом между сценариями: сервис выдаёт не больше 5 песочниц на IP. Зависимости сервиса объявляй в его `pyproject.toml`, даже если пакет уже есть в dev-окружении: тесты этого не поймают, поймает только контейнер (так было с `httpx` в Orders API).
- Docker Desktop на этой машине (кириллица в пути профиля): если загрузка образа зависла или Docker не стартует после перезапуска с ошибкой про `dockerInference` — закрыть процессы Docker, переименовать `%LOCALAPPDATA%\Docker\run` и `%LOCALAPPDATA%\docker-secrets-engine`, запустить снова; образы тянуть с `mirror.gcr.io/library/…` и перетегировать.

Форма контакта:

- `features/contact`: схема полей одна для браузера и сервера (`contact-schema.ts`); отправка — чистая `handleContactSubmission` с зависимостями (тестируется без сети); `actions.ts` только собирает зависимости. Заполненный honeypot и слишком быстрая отправка получают «отправлено» без доставки — бот не должен узнать, что пойман.
- Env читает только `lib/server-env.ts` (`import "server-only"`; в модулях, которые импортирует Vitest, `server-only` не ставь). Страница контактов статическая: форма есть, только если Telegram настроен при сборке; каналы (email, профили, запись) — только заданные, а если нет ничего, честное «still being set up». Rate limit — в памяти процесса, на serverless это лимит на инстанс.
- Тема обращения (`project` / `role` / `other`) — радиокнопки; ссылки ставят её через `?topic=` (читается в браузере через `useSyncExternalStore`, проверяется Zod). В аналитику уходит только тема, никогда — содержимое формы.
- e2e собирают проект с фейковым ботом (`webServer.env` в `playwright.config.ts`); тесты формы не должны доходить до Telegram — только валидация и honeypot.

## Next.js 16: что отличается от привычного

- Версионная документация лежит в `node_modules/next/dist/docs/`. Перед использованием незнакомого или изменившегося API читай соответствующий раздел, а не полагайся на память.
- Включены `cacheComponents` и `partialPrefetching`. Нестабильные данные (`fetch`, `cookies()`, `headers()`, `connection()`) — либо под `<Suspense>`, либо через `"use cache"` + `cacheLife`. Гайд: `01-app/01-getting-started/08-caching.md`.
- `middleware.ts` теперь называется `proxy.ts`.
- `params` / `searchParams` — Promise. Глобальные типы `PageProps<"/route">` и `LayoutProps<"/route">` генерируются `next typegen`.
- `dynamic(..., { ssr: false })` разрешён только внутри Client Component.
- `AGENTS.md` поддерживает `next dev` — не удаляй и не редактируй управляемый блок.

## Порядок работы над задачей

1. Изучи затронутую часть проекта и существующие решения. Не создавай вторую реализацию того, что уже есть (если есть `AssetManager`, не появляется `ResourceLoader`).
2. Продумай решение и regression risk, затем реализуй его полностью: без `// TODO`, псевдокода и заглушек.
3. Задача готова только когда проходят `npm run check`, `npm run build` и тесты (если есть), а изменённые страницы проверены в браузере без ошибок в консоли и в `get_errors`.
4. Найденную архитектурную проблему, которая не блокирует задачу, не чини попутно большим рефакторингом — сообщи о ней отдельно.
5. Вопросы задавай только по решениям, которые существенно влияют на архитектуру, игровой дизайн, данные, API, стоимость или безопасность. Остальное решай сам.

src/

  i18n/         # английский UI-словарь и хелперы языка (сайт одноязычный)

  simulation/   # чистый TS: граф системы, сценарии, runtime симуляции, SimEvent. Без React и Pixi
  engine/       # PixiJS-runtime, только клиент: core, iso, world, factories, views, systems, camera, input, modes, debug

Рядом с `src/` — `backend/` (Python, uv workspace: `libs/`, `services/`, `compose.yaml`, `scripts/`).

Направление зависимостей: `simulation` ← `engine` ← `features/stage` ← страницы. `simulation` не импортирует React и PixiJS, `engine` не импортирует React. Подробности — в разделе 8 концепции.

Папки создаются по мере необходимости, а не заранее. Каждая абстракция должна давать практическую пользу.

## Правила: Next.js и React

- Server Components по умолчанию. `"use client"` — только где нужны состояние, события или браузерные API; граница сервер/клиент проводится осознанно и как можно ниже по дереву.
- Мутации — Server Actions; route handlers — только когда действительно нужен HTTP-эндпоинт.
- Тяжёлые клиентские модули — через `next/dynamic` / `React.lazy` + Suspense.
- React отвечает за страницы, меню, HUD, формы, модалки, настройки. Никакого `setState` каждый кадр и никакой привязки отдельных спрайтов к React state.
- Секреты — только на сервере; в клиентский bundle попадают лишь переменные `NEXT_PUBLIC_*`.
- SEO для сайта и оболочки игры: Metadata API, canonical, Open Graph, JSON-LD, `sitemap.ts`, `robots.ts`, семантический HTML.
- Доступность DOM-интерфейса: семантика, навигация с клавиатуры, видимый focus, достаточный размер интерактивных элементов, aria только когда нужна.

## Правила: PixiJS / игровой слой

- PixiJS никогда не исполняется при SSR. Цепочка: Server Component → оболочка → Client Component с `dynamic(..., { ssr: false })` → PixiJS Application. Инициализация и `destroy` — в эффекте клиентского компонента.
- Связь React ↔ PixiJS — через отдельный слой состояния/событий (store или event bus), а не через пропсы на каждый кадр.
- Игровой цикл: delta time, fixed timestep для физики и критической логики, ограничение слишком большого delta, pause/resume по `visibilitychange`. Логика не зависит от FPS.
- Сцены через SceneManager с жизненным циклом `init → enter → update → resize → exit → destroy`. При уничтожении сцены снимаются listeners, ticker callbacks, таймеры, observers, освобождаются текстуры и контейнеры.
- Сущности — композиция компонентов (transform, sprite, velocity, health, collider…), а не глубокое наследование. Поведение — FSM (`idle/walk/attack/hurt/dead`), а не набор boolean-флагов. Полноценный ECS — только при реальной необходимости.
- Единый InputManager (pointer, touch, keyboard, multi-touch, pointercancel), игровая механика не подписывается на DOM-события напрямую. CameraSystem разделяет координаты screen / world / local.
- Ресурсы загружаются только через централизованный AssetManager: bundles по сценам, прогресс загрузки, кэш, обработка ошибок.
- Производительность: батчинг и атласы, pooling для часто создаваемых объектов (пули, частицы, враги, цифры урона), никаких аллокаций в каждом кадре, ограничение DPR (не рендерить в DPR 3–4), учёт средних Android-устройств, одна последовательная resize-стратегия.
- Коллизии: AABB / круги; spatial hash / grid / quadtree — при большом числе объектов. Физический движок — только если без него не обойтись.
- Анимации delta-safe; tween-библиотека — только если она оправдана.
- Debug overlay (FPS, frame time, счётчики сущностей/спрайтов/частиц, координаты) — только в development.
- Обработка отсутствия WebGL, потери контекста, ошибок загрузки и инициализации.

## Правила: TypeScript, данные, качество

- Запрещены `any`, `as any`, `@ts-ignore` (ESLint это ловит). Если `any` неизбежен из-за внешней библиотеки — объясни причину в комментарии.
- Используй discriminated unions, generics, `readonly`; const-объекты вместо `enum`, если так проще.
- Все внешние данные недоверенные (API, localStorage, URL-параметры, JSON, сохранения, ввод пользователя) — валидируй через Zod.
- Хранение: localStorage — небольшие настройки, IndexedDB — крупные локальные данные, серверная БД — только при реальной необходимости. Разделяй `GameState` / `SaveData` / `RuntimeState`, не сериализуй runtime целиком.
- Никаких пустых `catch`. Ошибки обрабатываются или пробрасываются с контекстом.
- Без god classes и файлов на 1000+ строк; у функции и класса одна понятная ответственность. Профессиональные имена (`playerVelocity`, `assetManifest`), без `data1`, `temp`, `doStuff`.
- Unit-тесты обязательны для расчётов, переходов состояний, генераторов, save/load, валидации. Раннер — Vitest, подключается вместе с первой такой логикой. E2E — там, где они дают реальную пользу.
