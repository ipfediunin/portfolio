## Проблема

Не всякую работу можно выполнить, пока клиент ждёт ответа на HTTP-запрос: обработка бывает долгой, зависит от внешних систем или затрагивает несколько сервисов. Если делать её синхронно, медленный или недоступный компонент тормозит всю цепочку. Нужна архитектура, в которой сервисы обмениваются сообщениями, а работа выполняется асинхронно.

## Моё участие

- Проектировал взаимодействие сервисов через брокеры сообщений.
- Организовывал передачу сообщений через RabbitMQ и работал с Apache Kafka.
- Реализовывал фоновую обработку задач и разделял компоненты системы по ответственности.
- Использовал Redis и PostgreSQL в составе таких систем.
- Анализировал ошибки обработки и доставки событий.

## Техническая архитектура

API → брокер сообщений → обработчик → база данных → уведомление. API принимает запрос и публикует сообщение, а работу выполняют обработчики, которые масштабируются независимо от API.

## Особенности реализации

- **Очередь и журнал — разные инструменты.** В очереди RabbitMQ сообщение достаётся одному обработчику и удаляется после подтверждения — так распределяется работа. В Kafka события хранятся в партициях topic, а каждая consumer group читает их со своей позиции и может перечитать — так одно событие получают несколько независимых потребителей.
- **Подтверждения.** Сообщение считается обработанным только после подтверждения; если обработчик упал раньше, сообщение достаётся другому.
- **Порядок.** В Kafka порядок гарантирован внутри партиции, поэтому события одной сущности публикуются с одним ключом.
- **Повторная доставка.** Из-за повторов обработчик может получить сообщение дважды — обработка должна это выдерживать.

## Результат

Сервисы обмениваются данными через брокеры сообщений, а длительная работа выполняется в фоне: API отвечает быстро, нагрузка распределяется между обработчиками, а события доступны всем сервисам, которым они нужны.
