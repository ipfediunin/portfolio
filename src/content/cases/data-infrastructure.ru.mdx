## Проблема

Данные приложения разнородны. Заказы и пользователи — это строгие связи и транзакции; похожие документы ищутся по смыслу; часть данных читается так часто, что каждый раз обращаться к базе дорого. Одно хранилище для всего этого не подходит, а подключения к нескольким облачным сервисам нужно настроить так, чтобы ими было удобно и безопасно управлять.

## Моё участие

- Проектировал структуру данных.
- Подключал backend-приложения к облачным базам данных.
- Работал с PostgreSQL для хранения структурированных данных.
- Использовал векторные хранилища — pgvector и Milvus.
- Работал с Redis.
- Настраивал взаимодействие компонентов и управлял конфигурацией подключений.
- Использовал облачные сервисы.

## Техническая архитектура

Web Client → Backend Services → слой данных: PostgreSQL для реляционных данных, pgvector или Milvus для векторного поиска, Redis для кэша, облачные сервисы. Backend определяет, какое хранилище подходит запросу.

## Особенности реализации

- **Хранилище под задачу.** PostgreSQL — связи, ограничения и транзакции; pgvector — поиск по векторам рядом с реляционными данными; Milvus — отдельное векторное хранилище для больших коллекций; Redis — быстрый доступ к часто читаемым данным.
- **Кэш.** Redis отдаёт часто читаемые данные без обращения к базе, а ограниченный срок жизни записей не даёт кэшу надолго расходиться с базой.
- **Конфигурация вне кода.** Адреса и параметры подключений задаются через окружение, поэтому одно приложение работает в разных окружениях без изменения кода.

## Результат

Backend-приложения работают с облачными базами данных и хранилищами, каждое из которых используется по назначению: реляционные данные, векторный поиск и кэш разделены, а подключения управляются через конфигурацию.
